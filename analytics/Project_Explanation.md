# Interview Explanations — SQL Data Warehouse Project

## Purpose of This Document

This file helps you explain every part of the project clearly and confidently during a
data analyst interview. Each section answers common interview questions using simple language
but stays technically accurate. Read this document alongside the SQL files, not as a
replacement for them.

## Part 1 — How the Bronze, Silver, and Gold Layers Work

### The simple explanation

Think of the warehouse like a water purification system:

- **Bronze** is the raw water — exactly what came out of the ground (the CSV files). No
  changes, no cleaning, just storage. If something goes wrong later, you can always come back
  to Bronze and see the original data.

- **Silver** is the filtered water — cleaned and standardized, but still recognizable as the
  same data. Here we fix typos, remove duplicates, standardize text values (e.g., `'M'` becomes
  `'Male'`), and validate dates. The data is now trustworthy.

- **Gold** is the purified drinking water — structured in a way that is easy for business
  users and analysts to query. At the Gold layer, Bronze/Silver tables are combined into a
  Star Schema of dimensions and a fact table.

### The technical explanation

| Layer | Objects | How it loads | Key transformation |
|---|---|---|---|
| Bronze | Tables (6) | Stored procedure with `BULK INSERT` | None — raw copy of CSV |
| Silver | Tables (6) | Stored procedure (`EXEC silver.load_silver`) | Deduplication, standardization, date validation |
| Gold | Views (3) | No load step — views compute on query | Star Schema joins, surrogate key assignment |

### Why three layers?

- **Auditability:** Bronze is the source of truth. You can always re-derive Silver from Bronze.
- **Separation of concerns:** Cleansing logic lives only in Silver. Business logic lives only in Gold.
- **Reliability:** If the Silver load fails halfway, the Bronze data is untouched.

### Common interview follow-up questions

**Q: Why are Gold objects views, not tables?**
A: Views read from Silver tables at query time and always reflect the latest Silver data.
   Because this project uses a full reload (truncate-and-replace) model, views are simpler
   than trying to keep a physical Gold table in sync. The trade-off is query performance:
   views recompute every time they are queried, whereas a physical table could be indexed.

**Q: What is a medallion architecture?**
A: Medallion architecture is the name for the Bronze–Silver–Gold layered approach. Each medal
   represents a stage of data quality and readiness. It is widely used in modern data engineering.

## Part 2 — Why the Gold Layer Uses Fact and Dimension Tables

### The simple explanation

A **dimension table** describes the *who*, *what*, and *where*:
- `gold.dim_customers` describes each customer (name, country, gender, birthdate).
- `gold.dim_products` describes each product (name, category, cost, product line).

A **fact table** records the *what happened* and *how much*:
- `gold.fact_sales` records each sales line item with quantity, price, and revenue.

The fact table uses **surrogate keys** (`customer_key`, `product_key`) to link back to the
dimensions. This arrangement is called a **Star Schema** because the fact table sits in the
center, and the dimension tables surround it like points of a star.

### Why not just put everything in one table?

Separating dimensions from facts:
- Avoids repeating customer and product details in every row of the fact table.
- Makes it easy to add new attributes to a dimension without changing the fact table.
- Allows analysts to filter and join efficiently.

### Common interview follow-up questions

**Q: What is a surrogate key?**
A: A surrogate key is an artificial integer (like `customer_key = 1, 2, 3...`) generated by
   the warehouse. The original source identifier (like `customer_id` from the CRM system) is
   also kept for traceability. Surrogate keys protect against changes in source system IDs and
   are always integers, which makes joins faster.

**Q: What is the grain of `gold.fact_sales`?**
A: One row per product within one order. This means a single order number can appear in
   multiple rows — one for each product in that order. This is important when calculating
   average order value (AOV): you must group by order number first, then average.

## Part 3 — The Eight Business Queries Explained

---

### Query 1 — Top 10 products by total revenue

**What problem does it solve?**
The business wants to know which products to protect, promote, and prioritize for inventory.

**How does the SQL work?**
1. Join `gold.fact_sales` to `gold.dim_products` on `product_key`.
2. Use `SUM(sales_amount)` to get total revenue per product.
3. Use `GROUP BY product_name` to aggregate at the product level.
4. Use `TOP (10)` with `ORDER BY total_revenue DESC` to show only the highest 10.

**Why this approach?**
`TOP` with `ORDER BY DESC` is the simplest way to rank in SQL Server. It is more readable
than a full ranking window function when you only need the top N records and do not need
to show the rank number itself.

**SQL concepts used:** `JOIN`, `GROUP BY`, `SUM`, `TOP`, `ORDER BY`

**Interview follow-up questions you may be asked:**
- What if two products have the same revenue at position 10 — which one wins?
  → `TOP` without `WITH TIES` picks one arbitrarily. Use `TOP (10) WITH TIES` to include both.
- Why do you join to `dim_products`?
  → The fact table stores `product_key` (an integer). The product name is in the dimension.
    Without the join, you would only see numbers, not names.

---

### Query 2 — Top 10 customers by total revenue

**What problem does it solve?**
Identifying high-value customers for retention, upselling, and priority support.

**How does the SQL work?**
1. Join `gold.fact_sales` to `gold.dim_customers` on `customer_key`.
2. Group by `customer_key`, `first_name`, and `last_name`.
3. Sum `sales_amount` and order descending, keeping the top 10.

**Why include `customer_key` in the GROUP BY?**
Two different customers could share the same first and last name. Including `customer_key`
ensures they are counted separately. Grouping only by name would incorrectly merge them.

**SQL concepts used:** `JOIN`, `GROUP BY`, `SUM`, `TOP`, `ORDER BY`

**Interview follow-up questions you may be asked:**
- Why not use `customer_id` instead of `customer_key`?
  → Both are available in `dim_customers`. `customer_key` is the surrogate key used in joins.
    `customer_id` is the original CRM identifier. Either works here, but `customer_key` is
    consistent with the dimensional model.

### Query 3 — Monthly revenue trend and month-over-month growth

**What problem does it solve?**
Understanding whether the business is growing, stable, or declining over time.

**How does the SQL work?**
Step 1 (CTE `monthly_revenue`): Truncate each `order_date` to the first day of its month using
`DATEADD(MONTH, DATEDIFF(MONTH, 0, order_date), 0)`. Group by that month and sum revenue.

Step 2 (Main SELECT): Use `LAG(monthly_revenue) OVER (ORDER BY month_start)` to get the
previous month's revenue in the same row.

Step 3: Calculate growth percentage as:
`(current - previous) / previous * 100`

A `CASE` statement handles two edge cases:
- The first month has no previous month → result is `NULL`.
- If previous revenue is 0, dividing would cause a divide-by-zero error → result is `NULL`.

**Why `DATEADD(MONTH, DATEDIFF(MONTH, 0, order_date), 0)`?**
This is the T-SQL idiom for "floor to the start of the month." It converts any date in
January 2023 to `2023-01-01`, which allows correct grouping and ordering. It is preferred
over `FORMAT()` because `FORMAT()` returns text, which sorts alphabetically and not
chronologically.

**SQL concepts used:** `CTE`, `GROUP BY`, `SUM`, `DATEADD`, `DATEDIFF`, `LAG` (window function), `CASE`

**Interview follow-up questions you may be asked:**
- What is a window function?
  → A window function performs a calculation across a set of related rows without collapsing
    them into one row (unlike `GROUP BY`). `LAG()` looks at the previous row in a defined order.
- Why is the first month's growth NULL?
  → There is no prior row for `LAG()` to read. This is correct behavior, not a bug.

### Query 4 — Product category performance and underperforming categories

**What problem does it solve?**
Helping the business understand which product categories need attention.

**How does the SQL work?**
CTE 1 (`category_revenue`): Aggregate total revenue per category.

CTE 2 (`category_summary`): Use `SUM(total_revenue) OVER ()` and `COUNT(*) OVER ()` — window
functions with no `PARTITION BY` — to calculate each category's share of total revenue and the
"equal share" (100% divided by the number of categories).

Main SELECT: Use a `CASE` statement to label a category `'Underperforming'` if its share is
below 50% of the equal share (`@underperformance_factor = 0.50`), otherwise `'Healthy'`.

**Why a share-based rule and not "80% of the average"?**
The earlier version compared each category with the average category revenue. One dominant
category (Bikes is about 96% of revenue) inflates the average and makes the comparison
misleading. The share-based rule is easier to explain. The 50% factor is a business
assumption; say so in the interview: "The business team would define the threshold."

**SQL concepts used:** `CTE`, `JOIN`, `GROUP BY`, `SUM OVER` / `COUNT OVER` (window functions), `COALESCE`, `CASE`, `ORDER BY`

**Interview follow-up questions you may be asked:**
- Could a category be underperforming because it has fewer products?
  → Yes. A proper analysis would also look at revenue per product and margin.
- What is `SUM() OVER ()`?
  → An aggregate window function. The empty `OVER ()` means: compute across the entire result
    set, so each row gets the same total and can be compared with it.

### Query 5 — Average order value (AOV)

**What problem does it solve?**
AOV is a core business KPI. Knowing it helps measure how much revenue each order brings in
on average, and whether promotions or upsells are working.

**How does the SQL work?**
CTE (`order_revenue`): Group the fact table by `order_number` and sum `sales_amount` to get
the total value of each order.

Main SELECT: Take `AVG(order_value)` over all orders.

**Why use a CTE instead of a direct `AVG(sales_amount)`?**
The fact table has one row per product per order. If order `SO001` has three products with
revenues of 100, 200, and 300, the row-level average would be 200. But the true order value
is 600, and if there are 1,000 such orders, the correct AOV should be based on 1,000 order
totals, not 3,000 row values. The CTE first collapses to order level, then averages.

**SQL concepts used:** `CTE`, `GROUP BY`, `SUM`, `AVG`

**Interview follow-up questions you may be asked:**
- What does AOV tell a business?
  → It tells how much a typical customer spends in one transaction. A higher AOV often means
    customers are buying more items or more expensive items. Businesses track AOV as a growth
    lever because increasing it does not require finding new customers.

### Query 6 — Sales and revenue by customer region

**What problem does it solve?**
Showing which geographic markets are most valuable, which guides marketing investment.

**How does the SQL work?**
1. Join `gold.fact_sales` to `gold.dim_customers` on `customer_key`.
2. Group by `c.country`.
3. Count distinct order numbers, sum revenue, and sum quantity.
4. Order by revenue descending.

**Why `COUNT(DISTINCT order_number)` and not `COUNT(*)`?**
One order can have multiple rows in the fact table (one per product). `COUNT(*)` would
count rows, not orders. `COUNT(DISTINCT order_number)` correctly counts unique orders.

**SQL concepts used:** `JOIN`, `GROUP BY`, `SUM`, `COUNT(DISTINCT)`, `ORDER BY`

**Interview follow-up questions you may be asked:**
- What about customers with no country data?
  → They appear as `'n/a'` in the results. The Silver load standardizes missing or empty
    country codes to `'n/a'`. The analyst should investigate how many customers fall into
    this group and whether the gap can be filled.

### Query 7 — Percentage of revenue from the top 10 customers

**What problem does it solve?**
Measuring revenue concentration risk. If a business depends heavily on a handful of customers,
it is vulnerable if any of them leave.

**How does the SQL work?**
CTE 1 (`customer_revenue`): Revenue per customer.

CTE 2 (`ranked_customers`): Assign a rank using `ROW_NUMBER() OVER (ORDER BY total_revenue DESC, customer_key)`.

CTE 3 (`total_revenue`): Calculate the grand total of all customer revenue.

Main SELECT: Use `CROSS JOIN` to bring the grand total into every row, then filter to
`revenue_rank <= 10` and sum. Divide by the grand total to get the percentage.

**Why `ROW_NUMBER()` with a tie-breaker and not `RANK()`?**
With `RANK()`, ties at the cut-off would return more than 10 customers. `ROW_NUMBER()` with
`customer_key` as a tie-breaker always selects exactly 10 and matches Query 2. (In this data the
highest two customers tie at rank 1, so tie handling matters.)

**SQL concepts used:** `CTE`, `JOIN`, `GROUP BY`, `SUM`, `ROW_NUMBER` (window function), `CROSS JOIN`

**Interview follow-up questions you may be asked:**
- What is a CROSS JOIN?
  → A CROSS JOIN produces one row for every combination of rows from the two tables. Here,
    `total_revenue` has exactly one row (the grand total). Cross-joining it to `ranked_customers`
    adds the grand total as a new column to every customer row without needing a join key.
- Why not use a subquery instead of a CTE?
  → CTEs are more readable and can be referenced multiple times. This query uses three CTEs
    and would be much harder to follow as nested subqueries.

### Query 8 — Customers who have not purchased recently

**What problem does it solve?**
Identifying customers at risk of churning so the business can take retention action.

**How does the SQL work?**
CTE 1 (`customer_last_purchase`): For each customer, find their most recent order date using `MAX(order_date)`.

CTE 2 (`latest_system_order`): Find the latest order date in the entire fact table. This
is used as the "as-of" date so the analysis is relative to the data, not to today's date.

Main SELECT: Filter to customers whose last purchase was more than 90 days before the latest
system order date. Sort by the longest gap first.

**Why compare against the latest order date in the data, not `GETDATE()`?**
The warehouse data has a fixed end date — it is not live. If you compare against today's
date, every customer who ever bought anything would appear inactive (because the data ends
months or years ago). Using the latest order date in the fact table gives a fair and
accurate recency comparison within the actual data window.

**SQL concepts used:** `CTE`, `GROUP BY`, `MAX`, `DATEDIFF`, `DATEADD`, `JOIN`, `CROSS JOIN`

**Interview follow-up questions you may be asked:**
- What does "recently" mean for this business?
  → I defined it as 90 days. For a business that sells fast-moving goods, 90 days is a long
    gap. For a business that sells bicycles (which people buy rarely), 90 days may be too
    short. The threshold is adjustable.
- How would you automate this for real business use?
  → This query could be wrapped in a view or scheduled as a report. The output could feed
    a CRM tool to trigger automated re-engagement emails.

## Part 4 — How Data Quality Tests Detect Problems

Each quality check in `additional_quality_checks.sql` tests one specific expectation.

| Check | What it tests | What a failure means |
|---|---|---|
| Duplicate customer keys | No two rows in `dim_customers` share a `customer_key` | The surrogate key logic in the view is broken |
| Duplicate product keys | No two rows in `dim_products` share a `product_key` | Product dimension rows are being repeated |
| Null mandatory columns | `customer_key`, `customer_number`, `product_key`, `product_name` are not null | A source record is missing a required field |
| Future or null order dates | No order dates are null or in the future | Date conversion in Silver went wrong |
| Negative or zero sales | No negative amounts, zero prices, or zero quantities | Silver recalculation did not catch bad source data |
| Orphaned fact records | Every `customer_key` and `product_key` in the fact table exists in the dimensions | A key mismatch between fact and dimension tables |
| Duplicate fact grain | No duplicate `order_number + product_key + customer_key` combinations | The same line item was loaded more than once |
| Row counts | Bronze, Silver, and Gold counts are consistent | Rows were lost or duplicated during the load |

**Important:** A failing check is a signal to investigate, not to automatically delete data.
Some results that look like duplicates may be valid business records. Always understand
the reason before taking corrective action.

## Part 5 — What Could Go Wrong During Repeated Data Loading

This project uses a **full reload** pattern: every pipeline run truncates the target table
and reloads all data from scratch. This is simple and reliable, but it has risks:

| Risk | Explanation |
|---|---|
| **Source file missing** | If a CSV file is not in the import directory, `BULK INSERT` fails and the Bronze table is truncated but not reloaded — it becomes empty. |
| **Source file format changes** | If the upstream team adds or removes a column from a CSV, `BULK INSERT` will fail or silently shift column values. |
| **Data volume changes** | If the source system exports fewer rows than expected (e.g., a filter was applied), the warehouse silently loses records. The row count check detects this. |
| **Surrogate key instability** | The Gold views generate `customer_key` using `ROW_NUMBER() OVER (ORDER BY cst_id)`. If a customer is added or removed from Silver, every customer's surrogate key may change. This would break any downstream system that cached the old keys. |
| **Timezone or date format changes** | The Silver load converts date integers in `YYYYMMDD` format. If the source system changes date format, `TRY_CONVERT` returns NULL instead of the correct date. |

## Part 6 — How the Pipeline Could Be Improved in a Real Company

The current pipeline is a solid starting point for a portfolio project. Here is how it would
evolve in a production environment:

| Current approach | Real-world improvement |
|---|---|
| Full truncate-and-reload | Incremental (delta) loading — only process new or changed records |
| Manual execution via `EXEC` | Scheduled execution with an orchestration tool (Apache Airflow, Azure Data Factory) |
| Row count checks in SQL scripts | Automated data quality monitoring with alerts when thresholds are breached |
| Surrogate keys from `ROW_NUMBER()` | Stable surrogate keys from a sequence or hash that do not change between runs |
| No load history or audit log | A pipeline metadata table that records the start time, end time, row counts, and status of every run |
| Gold as views | Materialized tables (or indexed views) for performance-sensitive queries on large datasets |
| Three schemas in one database | Separate databases or lakehouse layers for stronger isolation and access control |

## Part 7 — Quick Reference for the Interview

### Key terms to know

| Term | Simple definition |
|---|---|
| ETL | Extract, Transform, Load — the process of moving data from source to warehouse |
| Star Schema | A dimensional model with one fact table in the center and dimension tables around it |
| Surrogate key | An artificial integer used as the primary key in a dimension table |
| Grain | The level of detail represented by one row in a table |
| CTE | Common Table Expression — a named temporary result set within a SQL query |
| Window function | A function that runs across a set of rows related to the current row (e.g., `LAG`, `RANK`, `SUM OVER`) |
| AOV | Average Order Value — total revenue divided by the number of distinct orders |
| Churn | When a customer stops purchasing from the business |

### Three things to say if you are unsure

1. "I would run the query and inspect the actual results before drawing a conclusion."
2. "The threshold I used is a starting point; I would adjust it based on business input."
3. "I would look at this in the context of the data limitations I documented."
